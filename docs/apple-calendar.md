# Apple Calendar integration

## One permission, no calendar setup

EventKit is Apple's supported on-device calendar framework. After the user
grants full Calendar access, Mark-1 reads the events already visible
in Apple Calendar. It does not require a calendar with a special name, a
dedicated agent calendar, a secondary Apple Account, or invitations.

The product's five calendar categories are neutral defaults; they are not
imported from a contributor's or user's account:

- Work
- Study
- Exercise
- Appointments
- Errands

They are not Apple Calendar names. **Today** reviews the current local day
through now. **Last Week** and **Last Month** review the immediately preceding
completed calendar week and month. The app records its first-use date and
reports partial history honestly inside the review when the requested period
predates tracking. This expected first-use state is context, not a failed
analysis warning.

Calendar presence is evidence that time was scheduled, not proof that the
activity happened. Complete/Incomplete is a deliberate user choice available
for every visible event in today plus the previous six local dates and is
stored locally. A successful tap is shown immediately as a filled selection
with a saved label. Holiday calendars are omitted from rows, coach review
context, future availability, and local conflict searches, while an ordinary
event whose title mentions a holiday remains visible. The coach uses the
stored status as follow-through evidence. An ended unmarked event contributes
deterministic 70%-likely-missed evidence without being stored or presented as
user-confirmed Incomplete; an ongoing or future unmarked event is not scored.
Settings summarizes calendar scope as `All non-holiday calendars` instead of
displaying the raw number of EventKit calendar collections.

The app reads all visible events afresh when it launches or returns to the
foreground. It also refreshes immediately before a write. Changes made directly
in Apple Calendar therefore remain authoritative and appear in Mark-1 on the
next refresh.

## Scheduling

Reviewing a period never writes an event. A valid review returns exactly seven
suggestions; if seven mutually safe suggestions cannot be produced, it returns
none. If on-device validation rejects a suggestion batch, the analysis remains
visible while all seven suggestions are withheld with a precise reason. A safe
suggestion may repeat a selected category when the analysis supports it;
existing future events still block conflicting times. The user can approve the
exact batch with one **Add 7 to Apple Calendar** button. This explicit
confirmation—not a standing automatic-scheduling toggle—authorizes the
on-device write pipeline.

The pipeline uses the device's normal default writable calendar, the same
destination Apple Calendar uses for a newly created event unless the user
chooses another calendar. The app resolves that destination at write time and
does not ask the user to create or maintain a separate calendar.

If the default calendar is an iCloud calendar, Apple syncs the new event to the
user's other devices. If it is a local or another account's calendar, normal
Apple Calendar behavior applies. Mark-1 never receives the user's
iCloud password or calendar credentials.

Every proposal is treated as untrusted until it passes fresh EventKit conflict
checks and local time-policy validation. Weekday events must fit 6:00–8:00 AM
or 5:30–11:00 PM, and weekend events must fit 6:00 AM–11:00 PM. An ordinary
proposal may last from 15 minutes through the configured maximum. The stricter
60–120-minute weekend duration applies only to suggestions generated by a
Today, Last Week, or Last Month review. The protected meal windows are
7:45–8:15 AM, 11:30 AM–12:00 PM, and 7:00–7:30 PM every day.

Local validation reports the actual failing rule. Invalid time ranges, past or
out-of-window times, ordinary and review-specific duration limits, protected
meal overlap, disabled categories, fresh conflicts, invalid content, and
invalid reminders do not collapse into one generic scheduling error.

## Following up on an Incomplete event

After a timed event is saved as **Incomplete**, its row exposes **Add**. This is
separate from the review screen's **Add 7 to Apple Calendar** action. Add does
not move the source event or change its status. It creates an agent-owned copy
with exactly the same timed duration.

The app refreshes EventKit first, then finds the earliest conflict-free slot
that satisfies the active-hour, meal, break, and duration policies later
today. Tomorrow is searched only when today has no valid fit. If neither day
has room, the app reports that specific availability failure instead of
creating an unsafe event. All-day events have no exact timed duration for this
operation, so the app directs the user to reschedule those in Apple Calendar.

The copy is written to the device's current default writable calendar. A
stable agent-ownership marker makes repeated Add attempts idempotent: the app
reuses the already-created copy rather than making duplicates. After EventKit
saves successfully, a privacy-minimized SwiftData record links the source
completion identity to the created agent event. If that local record cannot be
saved, the app removes the EventKit copy; if removal also fails, it reports an
explicit untracked-write error. The original event and its Incomplete status
remain unchanged in every case.

Apple references:

- [Accessing Calendar with EventKit](https://developer.apple.com/documentation/eventkit/accessing-calendar-using-eventkit-and-eventkitui)
- [EventKit overview](https://developer.apple.com/documentation/eventkit)
- [`defaultCalendarForNewEvents`](https://developer.apple.com/documentation/eventkit/ekeventstore/defaultcalendarfornewevents)
- [`attendees` is read-only](https://developer.apple.com/documentation/eventkit/ekcalendaritem/attendees)

EventKit does not let the app silently add attendees. Invitees can be added
later in Apple Calendar if needed, but invitations are not required for the
normal Mark-1 workflow.

## Privacy-safe diagnostics

The app uses structured `os.Logger` categories named `lifecycle`, `calendar`,
`completion`, `scheduling`, `network`, `coach`, and `persistence`. These logs
record operational evidence such as intent flags, analysis period, snapshot
counts and truncation, HTTP status, validation outcome, and batch progress.
Completion identities are logged only as private hashed values, and error
domains are private.

The logs never contain chat text, provider request or response bodies, event
titles, notes, API keys, the app secret, model values, full URLs, raw calendar
identifiers, calendar titles, proposal rationales, session identifiers, or
installation identifiers.

## Background limitation

iOS background refresh is opportunistic, not an exact scheduler. Mark-1
refreshes Calendar when the app launches or returns to the foreground
and performs writes on-device while active. It relies on Calendar alarms or
local notifications afterward. Guaranteed unattended server-side calendar
operation is outside the current product and is not required for Today, Last
Week, or Last Month reviews.

- [Choosing background strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)
